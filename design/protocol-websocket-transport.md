# Protocol: WebSocket Transport

## Purpose

This protocol defines the transport rules for the TARS session protocol between TARS and the worker.

## Transport Choice

Use a single WebSocket connection per worker session.

This gives:

- full-duplex communication
- one long-lived connection per session
- natural streaming for logs and tool events
- natural server-initiated steering
- no bind-mounted runtime socket path
- no custom framing layer on top of the transport

## Roles

- TARS is the WebSocket server.
- The worker is the WebSocket client.

TARS hosts the endpoint on its existing control-plane HTTP server and allocates one authenticated session reservation per active worker run.

## Session URL

Example:

- base URL from worker perspective: `http://127.0.0.1:6767`
- upgrade path: `/tars-worker/ws`
- query params:
  - `sessionKey`
  - `token`

Illustrative URL:

- `ws://127.0.0.1:6767/tars-worker/ws?sessionKey=mbrooks%2Ftars%23395&token=<opaque-token>`

In Docker Compose, the worker can share the TARS container network namespace and use loopback. In other deployments, TARS may provide a different worker-reachable base URL such as `host.docker.internal`.

The token is generated by TARS when it launches the worker and is valid only for that pending session.

## Session Isolation

Each session gets:

- one dedicated `sessionKey`
- one opaque connection token
- one accepted worker connection

TARS should reject upgrades with:

- unknown token
- session key mismatch
- protocol version mismatch after connect
- a reused or unknown token, including an unexpected second client for the same live session

## Connection Lifecycle

1. TARS reserves a pending session connection and generates a token.
2. TARS launches the worker with `TARS_SESSION_WS_URL` and `TARS_SESSION_KEY`.
3. The worker opens the WebSocket connection and sends `hello`.
4. TARS validates the session key and returns `launch_config`.
5. The worker sends `ack`.
6. Session traffic continues until `complete` or shutdown.

## Message Encoding

Each WebSocket message carries one JSON object with:

- `type`
- `protocolVersion`
- `sessionKey`
- `messageId`
- `payload`

No extra newline or length-prefix framing is required.

## Ordering

Message order matters for:

- control messages
- event batches
- terminal completion

TARS should process messages in receive order per connection. The worker should process TARS control messages in receive order as well.

## Acknowledgements

The protocol supports explicit `ack` messages for:

- `launch_config`
- `control`
- optionally future resumability features

This keeps steering and stop semantics observable.

## Reconnect

V1 uses the simple policy:

- any disconnect is treated as session failure unless completion already arrived

This keeps the transport smaller and avoids reconnect state machines.

## Heartbeat

The worker sends explicit `heartbeat` messages so TARS can update session activity and distinguish a healthy idle worker from a stuck one.

## Shutdown

When the session ends:

1. The worker sends `complete` and closes its WebSocket during cleanup.
2. TARS closes any remaining connection and disposes the pending reservation.
3. The `docker run --rm` process removes the stopped worker container.

If the worker exits first, TARS rejects the execution and includes the captured Docker output tail when available.

## Observability

The WebSocket session is the authoritative control channel.

Worker stdout and stderr may still be captured by Docker for debugging, but TARS should not rely on them for correctness.
