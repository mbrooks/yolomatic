# Protocol: WebSocket Transport

Status: as-built design

Last verified: 2026-08-01 against `github/main` at `26171605efdd`

## Purpose

This protocol defines the transport rules for the Yolomatic session protocol between Yolomatic and the worker.

## Transport Choice

Use a single WebSocket connection per worker session.

This gives:

- full-duplex communication
- one long-lived connection per session
- natural streaming for logs and tool events
- natural server-initiated steering
- no bind-mounted runtime socket path
- no custom framing layer on top of the transport

## Roles

- Yolomatic is the WebSocket server.
- The worker is the WebSocket client.

Yolomatic hosts the endpoint on its existing control-plane HTTP server and allocates one authenticated session reservation per active worker run.

## Session URL

Example:

- base URL from worker perspective: `http://127.0.0.1:6767`
- upgrade path: `/yolomatic-worker/ws`
- query params:
  - `sessionKey`
  - `token`

Illustrative URL:

- `ws://127.0.0.1:6767/yolomatic-worker/ws?sessionKey=mbrooks%2Fyolomatic%23395&token=<opaque-token>`

In Docker Compose, the worker can share the Yolomatic container network namespace and use loopback. In other deployments, Yolomatic may provide a different worker-reachable base URL such as `host.docker.internal`.

The token is generated by Yolomatic when it launches the worker and is valid only for that pending session. The server consumes it before accepting the upgrade, so it cannot be reused.

## Session Isolation

Each session gets:

- one dedicated `sessionKey`
- one opaque connection token
- one accepted worker connection

Yolomatic rejects upgrades with `401 Unauthorized` for:

- unknown token
- session key mismatch
- a reused or unknown token, including an unexpected second client for the same live session

Protocol version and envelope session-key mismatches are checked after connect
and close that connection with a WebSocket policy/protocol error.

## Connection Lifecycle

1. Yolomatic reserves a pending session connection and generates a token.
2. Yolomatic launches the worker with `YOLO_SESSION_WS_URL` and `YOLO_SESSION_KEY`.
3. The worker opens the WebSocket connection and sends `hello`.
4. Yolomatic validates the session key and returns `launch_config`.
5. The worker sends `ack`.
6. Session traffic continues until `complete` or shutdown.

## Message Encoding

Each WebSocket message carries one JSON object with:

- `type`
- `protocolVersion`
- `sessionKey`
- `messageId`
- `payload`

No extra newline or length-prefix framing is required.

## Ordering

Message order matters for:

- control messages
- event batches
- terminal completion

WebSocket delivery preserves receive order, but the current host and worker
start asynchronous message handlers without a serial processing queue. Handler
work and acknowledgements can therefore overlap even though callbacks begin in
delivery order.

## Acknowledgements

The protocol supports explicit `ack` messages for:

- `launch_config`
- `control`
- optionally future resumability features

This keeps steering and stop semantics observable.

## Reconnect

V1 uses the simple policy:

- any disconnect is treated as session failure unless completion already arrived

This keeps the transport smaller and avoids reconnect state machines.

## Heartbeat

The worker sends a `heartbeat` every five seconds while its agent is running.
Yolomatic uses each heartbeat to update session activity. There is no
worker-protocol heartbeat timeout or watchdog today; stale-session handling is
owned by the broader control-plane session lifecycle.

## Shutdown

When the session ends:

1. The worker sends `complete` and closes its WebSocket during cleanup.
2. Yolomatic closes any remaining connection and disposes the pending reservation.
3. The `docker run --rm` process removes the stopped worker container.

If the worker exits first, Yolomatic rejects the execution and includes the captured Docker output tail when available.

## Observability

The WebSocket session is the authoritative control channel.

Worker stdout and stderr are captured in bounded tails for debugging, but
Yolomatic does not use them as the correctness protocol.
